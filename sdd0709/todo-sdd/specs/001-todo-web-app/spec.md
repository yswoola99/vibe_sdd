## 사용자 시나리오 및 테스트 *(필수)*

### 사용자 이야기 1 - 새 할 일 추가하기 (우선순위: P1)
사용자는 할 일 제목을 입력하고 추가하면 목록에 새 항목으로 표시된다. 빈 값이나 공백만 있는 입력은 거절되고, 사용자에게 안내 메시지를 확인할 수 있다.

**왜 이 우선순위인가**: 할 일 생성은 이 기능의 핵심 진입점이며, 이후 완료/삭제/필터 작업의 기본이 된다.

**독립 테스트**: 빈 목록에서 새 할 일을 하나 추가해 정상적으로 표시되는지, 그리고 공백 입력 시 추가되지 않는지를 검증하면 이 사용자 흐름을 독립적으로 테스트할 수 있다.

**수락 시나리오**:
1. **주어졌을 때** 빈 할 일 목록이 존재할 때, **어떻게 하면** 사용자가 유효한 할 일 텍스트를 입력하고 추가하면, **그 결과** 목록에 새 항목이 추가되고 화면에 표시된다.
2. **주어졌을 때** 입력창에 공백만 입력되어 있을 때, **어떻게 하면** 사용자가 추가를 시도하면, **그 결과** 항목이 추가되지 않고 안내 메시지가 표시된다.

---

### 사용자 이야기 2 - 완료 상태 관리와 삭제하기 (우선순위: P1)
사용자는 할 일을 완료 처리하고, 완료된 항목을 다시 미완료로 되돌릴 수 있다. 또한 삭제할 때는 실수 방지를 위해 확인 절차를 거친다.

**왜 이 우선순위인가**: 완료 토글과 삭제는 할 일 앱의 핵심 동작으로, 사용자가 항목을 관리하는 기본 기능이기 때문이다.

**독립 테스트**: 항목을 완료 처리하고 다시 미완료로 되돌리며, 삭제 확인 후 실제로 제거되는지 확인하면 이 흐름을 독립적으로 테스트할 수 있다.

**수락 시나리오**:
1. **주어졌을 때** 완료되지 않은 할 일이 하나 있을 때, **어떻게 하면** 사용자가 해당 항목을 완료 처리하면, **그 결과** 항목은 완료 상태로 표시되고 취소선과 흐린 색을 갖게 된다.
2. **주어졌을 때** 완료된 할 일이 있을 때, **어떻게 하면** 사용자가 해당 항목을 다시 미완료로 토글하면, **그 결과** 항목은 일반 상태로 복원된다.
3. **주어졌을 때** 삭제 가능한 할 일이 있을 때, **어떻게 하면** 사용자가 삭제를 시도하면, **그 결과** 삭제 확인 절차가 나타나고 확인 후에만 항목이 제거된다.

---

### 사용자 이야기 3 - 상태 요약, 필터, 영속성 및 반응형 사용성 (우선순위: P2)
사용자는 화면 상단의 남은 할 일 수를 확인하고, 전체/진행중/완료 필터로 목록을 볼 수 있다. 새로고침이나 서버 재시작 후에도 목록이 유지되며, 모바일 화면에서도 편리하게 사용할 수 있다.

**왜 이 우선순위인가**: 이 기능들은 사용 경험의 완성도를 높이고, 앱이 실제로 유용하게 쓰이게 만드는 핵심 보조 기능이기 때문이다.

**독립 테스트**: 할 일 추가/완료/삭제 후 남은 개수와 필터 결과가 즉시 반영되는지, 새로고침 후 데이터가 유지되는지, 360px 폭에서도 주요 기능이 접근 가능한지 확인하면 이 흐름을 독립적으로 테스트할 수 있다.

**수락 시나오**:
1. **주어졌을 때** 여러 개의 할 일이 있을 때, **어떻게 하면** 사용자가 추가/완료/삭제를 수행하면, **그 결과** 남은 할 일 개수는 즉시 갱신된다.
2. **주어졌을 때** 목록에 완료/미완료 항목이 모두 있을 때, **어떻게 하면** 사용자가 필터를 변경하면, **그 결과** 선택된 필터에 해당하는 항목만 표시된다.
3. **주어졌을 때** 사용자가 새로고침하거나 서버를 재시작한 뒤, **어떻게 하면** 페이지를 다시 열면, **그 결과** 이전에 저장된 할 일 목록이 유지된다.
4. **주어졌을 때** 화면 폭이 360px인 모바일 환경일 때, **어떻게 하면** 사용자가 주요 동작을 수행하면, **그 결과** 주요 UI 요소가 모두 접근 가능하고 잘리지 않는다.

---

### 엣지 케이스

- 입력값이 비어 있거나 공백만 있을 때는 항목이 추가되지 않아야 한다.
- 할 일이 하나도 없을 때는 빈 상태 안내가 표시되어야 한다.
- 필터가 특정 상태로 설정된 상태에서 항목이 없으면 빈 상태 안내가 적절히 표시되어야 한다.
- 삭제 확인 절차를 거치지 않으면 항목이 실제로 제거되지 않아야 한다.

## 요구사항 *(필수)*

### 기능 요구사항

- **FR-001**: 시스템은 사용자가 할 일 텍스트를 입력하고 제출할 수 있는 기능을 제공해야 한다.
- **FR-002**: 시스템은 빈 값 또는 공백만 있는 입력에 대해 항목을 추가하지 않고, 사용자에게 안내 메시지를 표시해야 한다.
- **FR-003**: 시스템은 사용자가 할 일을 완료 상태로 전환하고 다시 미완료 상태로 되돌릴 수 있는 기능을 제공해야 한다.
- **FR-004**: 완료된 항목은 사용자가 구분할 수 있도록 취소선과 흐린 색으로 표시되어야 한다.
- **FR-005**: 시스템은 사용자가 할 일을 삭제할 수 있어야 하며, 삭제 전 확인 절차를 거쳐야 한다.
- **FR-006**: 시스템은 화면 상단에 남은 할 일 개수를 항상 표시해야 하며, 추가/완료/삭제가 발생하면 즉시 갱신되어야 한다.
- **FR-007**: 시스템은 전체/진행중/완료의 3가지 필터를 제공해야 한다.
- **FR-008**: 시스템은 브라우저 로컬 저장소를 우선 사용해, 새로고침 또는 서버 재시작 후에도 할 일 목록이 유지되도록 저장해야 한다.
- **FR-009**: 시스템은 화면 폭 360px에서도 주요 기능이 자연스럽게 사용 가능하도록 반응형으로 동작해야 한다.
- **FR-010**: 할 일이 하나도 없을 때는 친절한 빈 상태 안내 문구를 표시해야 한다.

### 핵심 엔티티

- **할 일(Todo)**: 사용자가 관리하는 작업 단위로, 식별자, 텍스트, 완료 여부를 포함한다.
- **할 일 목록(Todo List)**: 여러 할 일 항목이 모여 있는 사용자 화면의 상태이며, 현재 필터와 남은 개수를 포함한다.

## 성공 기준 *(필수)*

### 측정 가능한 결과

- **SC-001**: 사용자가 새 할 일을 추가하고, 완료/취소/삭제를 수행하는 주요 동작을 2분 이내에 완료할 수 있어야 한다.
- **SC-002**: 사용자가 새로고침하거나 서버를 재시작한 후에도 저장된 할 일 목록이 유지되어야 하며, 유지된 항목 수가 초기 상태와 일치해야 한다.
- **SC-003**: 화면 폭 360px 환경에서도 할 일 추가, 완료 토글, 삭제, 필터 변경의 핵심 동작이 모두 접근 가능해야 한다.
- **SC-004**: 할 일이 없을 때 빈 상태 안내가 표시되고, 사용자가 다음 행동을 시작할 수 있는 명확한 안내를 제공해야 한다.

## 가정

- 대상 사용자는 개인이 자신의 할 일을 관리하는 단일 사용자로 가정한다.
- 데이터 영속성은 처음에는 브라우저 로컬 저장소를 사용하며, 사용자가 새로고침이나 재시작 후에도 기존 데이터에 접근할 수 있어야 한다.
- 반응형 동작은 모바일 화면에서도 핵심 기능 접근성을 보장하는 수준으로 정의한다.
- 기술 스택은 계획 단계에서 결정하며, 이 명세서의 범위는 사용자 요구사항과 품질 기준을 중심으로 한다.
